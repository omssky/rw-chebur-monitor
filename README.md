# rw-chebur-monitor

Небольшой Go-сервис: получает VPN-ноды из Remnawave, проверяет их клиентские адреса через динамический API Cheburcheck и сообщает о ТСПУ-блокировках в Telegram-топик. Один контейнер, SQLite, конфигурация через env.

## Развёртывание

Нужны Docker с Compose v2, API-токен Remnawave с доступом к чтению Nodes/Hosts и Telegram-бот с правом отправки сообщений в выбранный топик.

```bash
git clone https://github.com/omssky/rw-chebur-monitor.git
cd rw-chebur-monitor
cp .env.example .env
chmod 600 .env
nano .env
```

Заполните пять обязательных настроек:

- `REMNAWAVE_URL` — HTTPS-адрес панели **без `/api`**.
- `REMNAWAVE_API_TOKEN` — отдельный токен панели.
- `TELEGRAM_BOT_TOKEN` — токен бота.
- `TELEGRAM_CHAT_ID` — ID группы, обычно начинается с `-100`.
- `TELEGRAM_THREAD_ID` — числовой ID топика.

Ещё три настройки имеют значения по умолчанию: `CHECK_INTERVAL=30m`, `CONFIRM_DELAY=3m`, `DB_PATH=/data/monitor.db`. Интервал подтверждения должен быть от 15 секунд и меньше основного интервала. В готовом Compose оставьте базу внутри `/data`.

Готовый образ: `ghcr.io/omssky/rw-chebur-monitor:latest`, `linux/amd64` и `linux/arm64`.

GitHub изначально создаёт GHCR-пакет приватным. Если образ требует авторизацию, один раз выполните `docker login ghcr.io -u omssky`; вместо пароля используйте GitHub PAT **classic** с `read:packages`. Для публичного пакета вход не нужен. Видимость пакета настраивается отдельно от репозитория. GitHub-токен не относится к `.env` приложения.

```bash
docker compose pull
docker compose up -d
docker compose logs -f --tail=100 monitor
```

Приложение сразу запускает мониторинг. CLI-команд, веб-интерфейса и входящих портов нет. В логах видно число найденных целей, результаты запусков и ошибки внешних сервисов. Все временные метки в UTC. Токены скрываются.

## Поведение

1. На старте и каждые 30 минут сервис читает Nodes и Hosts Remnawave. Выбирает включённые Hosts, связанные с включёнными нодами и активными inbounds. Одинаковые адреса проверяет один раз, сохраняя имена связанных нод.
2. Запрашивает `/api/v1/check?target=…`, затем `/api/v1/probe/{id}`. Второй запрос запускает динамическую проверку и возвращает SSE — события с результатами отдельных сканеров.
3. Первое `tspu_block` назначает повторную проверку через 3 минуты. Второй результат от того же сканера в той же сети подтверждает блокировку и вызывает алерт.
4. Два последовательных результата с единственным вердиктом `ok` от затронутого сканера закрывают инцидент. В уведомлении о восстановлении указана длительность.
5. Повторяющиеся блокировки не спамят. Исчезнувший сканер, `uncertain`, смена ASN/региона, ошибка HTTP и обрыв SSE не считаются восстановлением. Если проблемная цель удалена/отключена, приходит сообщение о прекращении наблюдения.

Сканеры учитываются отдельно: доступность у большинства не скрывает блокировку у одного оператора. Два сканера одной сети могут дать два уведомления; ID сканера указан в сообщении. При отсутствующих данных инцидент остаётся открытым.

Проверки выполняются последовательно с промежутком минимум 15 секунд между запусками и общим таймаутом 3 минуты на цель. HTTP 429 откладывает все проверки с учётом `Retry-After`. Обычные ошибки повторяются через 1, 2, 4, 8, 16 минут, но не реже основного интервала. При долгих проверках фактический интервал увеличивается; параллельные циклы и накопленные за простой запуски не создаются.

Если Remnawave недоступна, используется последний сохранённый список; синхронизация повторяется через 5 минут или раньше при меньшем основном интервале. Ошибки и пустой инвентарь видны в логах.

## SQLite и доставка

В базе две таблицы: текущее состояние и очередь неотправленных сообщений. Изменение инцидента и создание уведомления записываются одной транзакцией. Перезапуск сохраняет состояние, подтверждения, очередь и сроки повторов. Доставленные сообщения удаляются из очереди; архив всех проверок не ведётся.

Уведомления отправляются по порядку, с повторными попытками и учётом лимитов Telegram. Ошибка отправки не останавливает мониторинг. Если Telegram принял сообщение, а процесс завершился до записи этого факта в SQLite, возможна повторная доставка.

Один экземпляр сервиса на базу; от случайного второго запуска защищает файловая блокировка. SQLite работает в WAL-режиме, данные лежат в named volume `monitor-data`. `docker compose down` сохраняет volume, **`docker compose down -v` удаляет его**. Для простого бэкапа остановите контейнер и сохраните весь volume.

## Ограничения

- Cheburcheck проверяет признаки сетевой блокировки у своих сканеров. Это не полноценная проверка VLESS/Reality и не гарантия доступности VPN у всех операторов.
- Статическое поле `blocked` не вызывает алерт — используется только динамический `tspu_block`.
- API Cheburcheck не даёт задать произвольные IP/SNI/порт. Hosts не на 443, неподдерживаемые и шаблонные адреса пропускаются с предупреждением. Несовпадение address/SNI отражается в логах.
- Изученная реализация использует первый разрешённый IP для части тестов домена: все адреса многозаписного DNS не покрываются.
- Для IP-цели Cheburcheck может возвращать `uncertain` вместо `ok`. Такой результат не закроет инцидент автоматически; домены подходят лучше.
- Полную остановку сервера или самого монитора нужно отслеживать внешними средствами.

## Обновление и разработка

```bash
docker compose pull
docker compose up -d
```

После успешных тестов GitHub Actions собирает образ для двух архитектур и публикует его в GHCR. `latest` соответствует default branch; также доступны `sha-<полный SHA коммита>`. Git-тег `v1.2.3` создаёт образ `:1.2.3`. Нужен только встроенный `GITHUB_TOKEN`, без дополнительных секретов. На pull request образ собирается без публикации.

Для фиксированного образа задайте `IMAGE=ghcr.io/omssky/rw-chebur-monitor:sha-…` при запуске Compose или добавьте эту переменную в `.env` — она используется только Compose.

```bash
go test -race -count=1 ./...
go vet ./...
docker build -t rw-chebur-monitor:local .
IMAGE=rw-chebur-monitor:local docker compose up -d
```

Go 1.26.2+. Код организован по назначению:

- `internal/monitor` — правила инцидентов, расписание и интерфейсы внешних зависимостей;
- `internal/remnawave`, `internal/cheburcheck`, `internal/telegram` — клиенты сервисов;
- `internal/sqlite` — хранение состояния и очереди;
- `internal/config` — чтение и проверка env;
- `cmd/monitor` — сборка зависимостей и обработка завершения процесса.

Библиотеки: `caarlos0/env/v11`, `go-telegram/bot`, `tmaxmax/go-sse`, `modernc.org/sqlite`, `x/sync/errgroup`. Версии закреплены в `go.mod`/`go.sum`.

Go SDK в [docs.rw](https://docs.rw/sdk/go-sdk/) — community и привязан к версии панели. Для двух GET используется небольшой HTTP-клиент с минимальными моделями API 3.x: это проще большого SDK другой версии. Совместимость с конкретной панелью видна по первому циклу и логам синхронизации.

Источники: [Remnawave Hosts](https://docs.rw/learn-en/hosts/), [Nodes](https://docs.rw/learn-en/nodes/), [Cheburcheck API](https://github.com/LowderPlay/cheburcheck/blob/9ae4b661ba3a0bf467f8d16bf5a2539a6af06d8e/website/src/api/probe.rs), [Telegram](https://core.telegram.org/bots/api#sendmessage), [GHCR](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry).
